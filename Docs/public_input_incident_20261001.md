# US·KR 공개 입력 접근/신선도 장애 감사 및 수정

검사 구간: 2026-10-01 14:35~15:05 UTC. 이 문서는 투자 보고서가 아니며,
계좌번호·원시 증권사 응답·인증정보를 포함하지 않는다.

## 확인된 원인

1. **경로별 도구 차이**: 웹 조회에서 Pages llms.txt, Work status.html 및
   GitHub ref API가 `not accessible via this tool`로 반환되었다. HTTP 코드는
   제공되지 않았다. raw discovery는 이번 검사에서는 정상 조회되었다.
   이를 저장소 404/403, robots 차단, 생산 중단으로 단정할 근거는 없다.
   연결된 GitHub fetch/fetch_file로 공개 ref·안내문·고정 커밋 파일은 읽혔다.
2. **렌더링과 바이트의 혼동**: 웹 본문만으로는 원시 SHA-256 검증을 할 수 없다.
   GitHub fetch_file의 base64 응답을 디코딩하면 원시 바이트 검증이 가능했다.
   blob SHA, 데이터 commit SHA, HEAD commit SHA, SHA-256은 서로 다른 값이다.
3. **게시 성공과 원자료 갱신의 혼동**: 공개 데이터 commit
   `fac9132d7f84ee798dcdf20d3dcd612c3d4be32f`의 manifest와 US/KR TXT/JSON
   4개 모두 길이·SHA-256이 일치했고 TXT는 JSON의 렌더링과 정확히 일치했다.
   확인한 HEAD `3aaeee7c37c42a2c9ea5e06f54eb9efead424247`의 안내문도 같은
   부모 데이터 commit을 가리켰다. 14:19:40 UTC 생성 문서지만 14:40:24 UTC
   기준 US 시세 19.51시간·계좌 15.98시간, KR 시세 8.24시간·계좌 8.16시간
   경과였다. 문서만 새로 만들어도 현재 개인화 입력이 되지 않는다.
   KR은 검사 시점 폐장 상태로, 이 경과 자체를 장중 장애라고 판정하지 않는다.
4. **생산자 병목**: [US 장중 작업](https://github.com/nornen0202/TradingAgents/actions/runs/36874218197)은
   14:10 UTC부터 `self-hosted, Windows` 실행기를 기다렸다.
   [US 정규 분석](https://github.com/nornen0202/TradingAgents/actions/runs/36858002348)은
   11:52 UTC부터 `desktop-gheeibb-codex`에서 진행 중이었다.
   [동시 Pages 작업](https://github.com/nornen0202/TradingAgents/actions/runs/36875159969)은
   별도 `tradingagents-pages` 라벨 실행기에서 성공했다. 관측 가능한 원인은
   장중 작업의 실행기 배정 지연이며, 전체 실행기 수나 서버 고장은 단정하지 않는다.
5. **만료 시 표시 불일치**: `_apply_market_row_validity`는 준비 플래그만 끄고
   BUY_NOW·현재 실행 가능 문구와 POSSIBLE을 남겼다. 공개 KR 자료에서 재현했다.
6. **값의 불일치**: 공개 US의 한 행은 VWAP가 같은 행의 일중 고가보다 높았다.
   어느 공급자·세션 값이 잘못됐는지는 이 공개 축약본으로 확정할 수 없다.
   이를 정상 실행 데이터로 허용하지 않는 검사가 필요했다.
7. **진짜 미공개 필드**: 미체결, 원통화 현금/동시점 환율, 정확한 비용·위험예산,
   일부 공급자/시장 상태는 축약 원문에 없었다. 연결 경로를 바꿔도 이 값을
   만들 수 없으며, 과거 계좌나 총자산 잔차로 보충해서는 안 된다.

## 이번에 적용한 수정

- 클라우드 US·KR 프롬프트를 v8로 업데이트하고 재조회하여 본문 일치 확인.
  제목·실행 일정·활성 상태는 불변. 일반 읽기는 GitHub 연결 도구 우선,
  없는 환경에서는 공개 웹 안내문을 사용한다. 접근 거부/DisabledError는
  우회하지 않는다. 일시적인 통신·렌더링 실패만 허용 경로에서 한 번 재시도한다.
- 원시 base64 해시, HEAD/부모 snapshot 구분, 독립 시계의 경과시간, 오류 종류,
  미확인 분모·수량·비용·사용자 한도의 정직한 표기를 명시했다.
- CLI 검증도 HEAD의 discovery를 읽고 안내문→manifest→TXT/JSON 전체 해시 체인을
  검증하도록 맞췄다. 기존 최신 HEAD 재확인과 원자료 만료 차단은 유지한다.
- 시세 누락/비정상 수치, 같은 세션 고저/VWAP 모순, 실행 라벨 모순을 차단한다.
- 만료된 행의 현재 라벨과 promotion을 함께 낮춘다. 분석 thesis는 유지하고
  원전략은 명시적인 reference_strategy로 보존한다. 공개 축약본에는 기존 공개
  데이터의 제한된 필드만 전달하며 계좌 식별정보는 추가하지 않는다.
- 검증 영수증에는 민감정보 없는 시계별 경과시간과 관측 개수를 추가한다.

## 검증과 남은 운영 조건

- 다운로드한 실제 원시 바이트를 로컬 검증기에 읽기 전용으로 재생했다.
  두 시장 모두 무결성은 통과하지만 REFERENCE_ONLY로 판정되고 개인화 입력은
  반환되지 않는다. 이는 올바른 차단이며 정상 입력처럼 승격하지 않았다.
- 관련 회귀 테스트는 해시 손상, manifest 손상, HEAD 이동, 날짜/계좌/가격 누락,
  표시 모순, 만료 후 thesis 보존, 공개 개인정보 차단을 포함한다.
- 관련 테스트 178개와 정적 검사가 통과했다. 전체 Linux 회귀검사에서는
  1,532개 통과·11개 건너뜀·104개 하위 검사 통과를 확인했다. 이 수치에서
  제외한 기존 Windows 모의 테스트 2개는 최초 전체 실행에서 Path.home()
  해석 오류로 실패했다. 해당 테스트와 codex_binary.py는 기준 main과 동일하며,
  이번 수정으로 전체 테스트가 무조건 통과했다고 주장하지 않는다.
- 실행기 대기 해결에는 장중 갱신용 실행기의 실제 가용성·공유 archive 접근·
  기존 API 자격증명 사용 범위 검증이 필요하다. Pages 실행기의 라벨만 보고
  장중/증권사 작업을 이동시키거나 정규 분석을 강제 종료하지 않았다.
- 현재 예약 저장과 대화 내 읽기 검증은 다음 백그라운드 실행의 도구 제공·
  성공적 보고서 전달을 보장하지 않는다. 다음 실제 실행 결과를 구분해 확인해야 한다.
- 신선도 예산(30분/36시간), 정규장 실행 조건, 자동 주문 금지, 비용·위험예산
  검증은 완화하지 않았다. 누락된 시장 상태/개인 한도는 계속 미확인이다.

## 운영 복구 완료 판정

1. 실제 호스트에서 장중 작업용 runner의 온라인·idle 상태와 archive 경로를
   확인한다. 별도 프로세스로 분리할 경우 저장소 checkout/출력 경로 충돌을
   막고, 기존에 승인된 자격증명의 사용 범위를 바꾸지 않는다.
2. 전용 runner를 준비한 뒤에만 overlay의 runs-on을 해당 라벨로 고정한다.
   라벨 변경만으로는 실행기가 생기지 않으며, queued 작업을 재실행해도
   가용 실행기가 없으면 동일한 문제가 반복된다.
3. 실제 정규장 갱신 이후 계좌·시세 시각, 새 공개 snapshot의 무결성, 실행
   라벨 정합성을 확인한다. 그 다음 US·KR 예약 보고서가 각각 새 입력을
   사용했는지 확인해야 종단 간 복구 완료다. 예약 저장 성공은 이 검사를
   대체하지 않는다. 이 감사에서 호스트 제어와 예약 강제 실행은 하지 않았다.
