# 보관 차트의 세대 전달·비동기 조회 검증

2026-10-26. PR458의 정산·시장별 원장 분리를 배포한 뒤 실제 8766 화면을 검사했다. 소스·읽기 전용 운영 API 128개와 원래 승인/7작업/정상 원장 소유권·정책·수량 비교 9개는 통과했으나, 실제 차트는 완료되지 않았다. 이 실패를 배포 성공으로 덮지 않는다.

## 확인한 실패와 측정 한계

390px 흐름은 최초 유용한 표시 약294ms, 정상 전략 카드 약681ms였고 131종목 목록 완료까지55.53초였다. 목록은 202를71회 받은 뒤200을 받았다. 이어 snapshot에서 다시202를4회 받은 뒤 마지막 요청이15.005초에 중단됐다. 1440px의 목록은2.807초였지만 snapshot이202 한 번 뒤15.015초 timeout으로 끝났다. 두 흐름 모두 정상 전략 체결0·실계좌 비활성·가이드·표 가독성은 표시됐으나 차트 완료 검증은 실패다.

목록 완료 후 snapshot에 목록 세대가 전달되지 않아 다시 스캔하는 코드와 진행 수의 초기화가 일치했다. index 이후 자료 선택·coverage·원장 replay·차트 생성이 동기 처리되는 경로도 확인했다. 마지막15초를 특정 함수·디스크·다른 앱 탓으로 단정하지 않는다.

별도 진단은 전체 archive를 다시 탐색하지 않고 알려진 원본 한 개씩만 읽었다. AAPL 지정 원본은697,329bytes/260봉, KR 지정 원본은185,966bytes/289봉이었다. 계측된 snapshot은 각각1.66초/8.47초였고 KR의 달력 문맥 계산은7.70초를 차지했다. cProfile 오버헤드와 다른 입력 선택·캐시 상태가 있으므로 실제 UI의 지연 원인·상한·p95 또는 개선율을 증명하지 않는다. 이 진단은 정상 연구·승인·체결의 증거가 아니다.

## 조회 계약

- 목록의 200과202 모두 `X-Archive-Catalog-Generation`을 제공한다. 화면은 같은 조회의 snapshot에 이 세대를 전달한다. 첫 요청부터200인 작은 archive도 포함한다.
- snapshot의 자료 선택·coverage·원장 replay·차트 생성·직렬화·원문 검증은 서버의 작업 한 개에서 진행한다. HTTP는 짧은202와 단계·대기시간을 반환하고 같은 조건의 poll은 같은 작업을 읽는다.
- **HTTP snapshot은 명시적인 과거·시간대 있는 `as_of`가 필요하다.** 이전의 snapshot `now` 기본값은 제거한다. 일반 목록/health의 기본값과 직접 호출 CLI 함수는 유지한다. 실제 화면은 원래부터 명시 시각을 사용한다.
- 202의 `job_token`은 `snapshot_job`으로 전달한다. 종목·원래 UTC 기준 시각·anchor·목록 세대가 일치해야 한다. 다른 탭의 목록 갱신이 진행·대기 중인 작업의 세대 참조를 없애지 않는다.
- 본문에 원래 조회 기준 시각을 표시한다. 작업 완료 시각으로 시세·연구·승인·신선도를 갱신하지 않는다. 저장된 실행 엔진 판단과 원래 PIT 검증을 유지한다.

```text
GET /api/tickers?as_of=2026-10-25T17:00:00Z
# 응답의 실제 X-Archive-Catalog-Generation 값을 N으로 사용
GET /api/snapshot?ticker=AAPL&as_of=2026-10-25T17:00:00Z&catalog_generation=N
# 202 응답의 job_token을 TOKEN으로 사용, 원래 조건 그대로 poll
GET /api/snapshot?ticker=AAPL&as_of=2026-10-25T17:00:00Z&catalog_generation=N&snapshot_job=TOKEN
```

## 자원·무결성 경계

서버당 worker1개와 최대4작업으로 제한한다. 직렬화 결과는 한 건8MiB·합계16MiB 한도이며 큰 원문을 잘라 성공처럼 내보내지 않는다. 이 수는 프로세스 전체 메모리 한도가 아니다. 목록 projection과 진행 작업의 세대 참조 등은 별도이며 작업 수로 제한된다. 완료됐지만 수령되지 않은 작업은 새 입장 시 회수할 수 있어 영구적인 용량 정체를 막는다.

완료 응답은 같은 작업의 검증 후 한 번 전달한다. 소비·만료된 token은410, 다른 조건은400, 새 요청의 오래된 세대는409, 활성 작업 포화는429다. 통신 실패 후에는 새 조회가 필요하다. 공개 취소 HTTP는 제공하지 않는다. 이 기능은 보관자료 읽기 전용이며 주문을 전송하지 않는다.

선택 ticker tree·명시 manifest·고정 journal 경계와 파일 식별자를 검증한다. 이것을 CAS 전체 또는 archive 전체의 원자적 snapshot 증명으로 표현하지 않는다. 원장 metadata 변경은 원래 cutoff의 기존 replay와 비공개 admitted-row proof를 재검증해 정상 미래 append와 과거 가용 증거 변경을 구분한다. ACCOUNT_SEED 원문·경로·비공개 proof는 HTTP에 노출하지 않는다. 검증 도중 다시 변경되면 최대2회 안에서 확인하고, 안정된 증거를 얻지 못하면 실패한다. 파일 시각은 무효화·무결성 검사에만 사용한다.

브라우저의 요청당15초·202 전체 대기120초 예산은 유지한다. 금융 자료의 원래120초 신선도, 계좌·소유권·승인·원장·한도는 변경하지 않는다. 가격·계좌·주문 cache나 승인 경로를 추가하지 않는다.

## 검증 범위

느린 builder의 bounded202·단일 작업 join, 독립 health, 서로 다른 시점/종목/anchor/token, 미래·잘못된 날짜, source/경계/원장 교체, 미래 append 허용과 가용 증거·seed 변조 거절, 검사 중 추가 변경, 세대 회수와 queued 작업, 미수령 완료 작업 회수, 용량·만료·단회 전달을 fixture로 확인한다. 직접 API에서 명시 시각 누락은 작업 입장 전에 거절한다. 360/390/430/1440px 화면·Node 가상 시계 검증은 실제 운영 성능과 구분한다.

최종 정확한 head CI·병합·소스 잠금 배포와 새 실제 8766 국내·미국 화면 검증은 별도 영수증으로 확인한다. 이전 실패 원본을 보존한다. 읽기 성공·테스트 수는 정상 전략 BUY/SELL 체결이나 비용 후 수익·실투자 준비 완료를 뜻하지 않는다.
